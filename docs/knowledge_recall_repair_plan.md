# 知识关联与检索筛选修复方案

本方案针对100题实际使用的0.6B冻结目录及其下游链路。当前已确认的主要缺口是：38条地标坐标没有任何表关联；10条医院定义只有5条具备对应ES表的检索资格；48条海事资料只有1条具备对应PG表的检索资格。问题集中在知识可检索性，不能仅用表覆盖率衡量修复效果。

本文件为实施方案，尚未修改生产代码、原始资料、模型或训练答案。

## 1. 调整职责与数据契约

| 层次 | 修复后的职责 | 需要取消的耦合 |
| --- | --- | --- |
| 原始知识 | 保存全部ID、原文、来源和哈希，所有条目进入知识索引 | 无表关联就失去检索资格 |
| 程序关联 | 依据原文引用、字段、注释、字典值及允许训练划分提供可审计关联 | 每表必须固定关联12条 |
| 模型候选 | 保存embedding/RRF/重排产生的相似候选及分数 | 将实验候选直接当作确定适用范围 |
| 问题级召回 | 用问题直接检索知识全文，结合表关联扩充候选 | 先选表，再只在这些表的关联知识中查找 |
| 精排与组装 | 判断问题相关性、记录适用范围与冲突，按预算选择原文 | 将非空知识块当作必要知识已经齐全 |

遵守现有AGENTS.md与预处理规范：生产关联器保持纯程序，不调用LLM、不读取审核标签。模型用于问题级候选召回和排序；模型实验关联保留为候选。审核结果仅进入独立评价入口。

建议增加独立元数据，保留现有`tables[].knowledge[]`的ID与完整原文格式：

- `catalog_table_ids`：程序关联目录接受的关系；“程序接受”不等于人工确认其全部内容正确。
- `candidate_table_ids`：模型实验得到的候选关系，来源与版本单列。
- `scope_evidence`：可直接定位的原文范围证据，例如明确库表引用；不能由相似候选反推为确定范围。
- `quality_issues`：比较符缺失、字段/单位冲突等已检测问题及原文位置。

无关联表示范围未知，不等于全局适用，更不等于应丢弃。原始事实不因范围未知而被改写或自动补全。

## 2. 保留有依据的关联，解除固定Top12限制

`data/association.py`已有纯程序关联与审计机制，可作为接受关联的基础。继续允许零关联、一条知识关联多表，不为补数量降低阈值；现有阈值先保持，另行评估质量后再调整。

`experiments/prompt_coverage.py:model_catalog`生成的模型Top12结果应保存到候选关联文件，避免覆盖或混同程序接受关联。历史实验产物保留原样，新目录标记新版本。

地标坐标、区域边界等知识可以保持无表关联，由问题级全局召回发现。不必为了使“天府广场坐标”可被医院题检索，就将所有地标强行关联到医院表。

原文明确提到其他库表，或只有位置/时间等通用词面相近的旧来源知识，应携带来源和适用证据参与筛选。旧来源ID本身不作为剔除条件；不将本轮发现的ID范围写成生产白名单。

## 3. 分开处理知识、Schema和案例的筛选

在`retrieval/index.py`增加知识专用召回入口，避免直接修改通用`search`条件后影响所有文档。

| 文档类型 | 范围规则 |
| --- | --- |
| Schema | 保持引擎边界及现有表检索逻辑 |
| 训练案例 | 保持已有单步/联邦步骤与系统匹配规则 |
| 知识 | 全局通道不依赖关联表或推断引擎；关联通道使用关系提供候选和范围证据 |

对知识取消以下否决依据：`engines=[]`、没有与已选表重叠、以及模型候选推断出其他引擎。不能简单对所有文档把系统集合的子集判断替换成交集判断，联邦案例仍需要完整的步骤系统约束。

确有多个适用系统的知识，命中其中一个系统不应因还关联了另一个系统而被排除。此规则只说明候选资格，不代表整条知识的每个片段都适用于当前系统。

如后续需要硬排除，必须有可审计的明确不适用证据，不能把弱关联或原文范围缺失当作排除依据。未知范围进入全局排序，通过相关性、来源范围与上下文预算控制噪声。

## 4. 问题级多路召回、统一重排

第一轮建议保留0.6B embedding与reranker，参数作为可比较的起点：

| 候选来源 | 初始配置 | 目的 |
| --- | --- | --- |
| 全局BM25 | 在全部knowledge中取50 | 命中概念名、地标名、字段和代码 |
| 全局embedding | 在全部knowledge中取50 | 补充表达差异 |
| 两路RRF融合 | k=60，融合后保留50 | 形成独立于表关联的主要候选池 |
| 已选表的关联知识 | 按问题相关性保留最多20 | 补充定义、单位和字段映射 |
| 原文概念/实体名称匹配 | 最多10 | 补充稀有专名，避免被语义相近材料挤出 |

实体或概念名必须从原始资料中的名称、标题、明确别名提取；不得人工添加当前错题的地标、医院类别或知识ID映射。匹配只是增加候选，不能直接认定适用或保证最终入选。

三组来源合并、按knowledge_id去重后最多80条。关联与名称通道不能在合并时挤掉全局50条；精排应覆盖整个合并候选池，避免复用当前`rank_hits`时又在评分前截回50条。RRF分数和重排原始分数分别保存，不直接相加，也不将原始logit当概率。

80条应作为知识专用的精排候选上限配置，不能直接调大共用`rerank_top_k`而连带改变Schema和训练案例的候选池，否则首轮无法隔离知识召回的效果。

第一轮继续用原问题进行精排。加入表摘要、范围分数等调整应作为后续独立消融，避免一次改变过多因素。

提示词最终知识预算先保留最多12条，与旧版进行同口径比较。固定每表12条关联应取消；提示词最多12条是另一层预算，可以保留。后续依据独立标注开发数据校准最低相关性阈值与需求覆盖策略，允许少于12条，不强行填满。参数选择报告为开发成绩，不能把开发标签传给检索代码。

## 5. 组装完整事实，传递范围与冲突

`retrieval/context.py:assemble`接收全局知识候选和关联候选，统一选择后发送完整`knowledge_text`，保留ID、来源、命中通道、排序和版本信息。候选按ID去重；不同条件和阈值的相似知识不能仅因主题相近被去重。

知识问题的处理原则：

- 明确Schema字段/结构冲突：以Schema为准，保留冲突原文与不采用依据。
- 比较符残缺、相互矛盾：传递问题标记，不能自动补造比较符或偷偷合并冲突条件。
- 特殊业务定义：依据原文判断适用范围，不能因为与常识不同就改成常规公式。
- 全局召回得到原文中明确的表引用：可为后续补表提供线索，不自动创建知识关联。

首轮修复冻结路由与Schema候选表，只调整知识召回，以隔离效果。之后再比较“知识辅助补表”：将明确引用的表加入候选池，与Schema召回结果统一评估，不直接按目录顺序替换表；只允许一轮扩展，避免循环放大弱关联。

冻结表候选取自旧版真实流程输出，不用参考答案补表；端到端回归则重新运行完整检索流程，两个口径分别报告。

## 6. 实施顺序与代码落点

| 阶段 | 主要工作 | 预期产物 |
| --- | --- | --- |
| A：解除召回阻断 | 增加全局知识入口；取消知识的空引擎/已选表硬门槛；增加召回与剔除日志 | 原表候选固定的全局知识召回版本 |
| B：理清关联语义 | 程序关联与模型候选分别保存；废止模型Top12覆盖接受关联；重建索引元数据 | 来源和范围可追踪的新目录/索引 |
| C：控制提示词噪声 | 合并候选全量精排；需求覆盖、相关性阈值及冲突标记消融 | 新提示词及逐知识选择理由 |
| D：评估知识辅助补表 | 将原文明示表引用作为扩表线索；检查同系统跨业务库和跨系统问题 | 库表与知识联合覆盖报告 |

主要涉及`data/association.py`、`experiments/prompt_coverage.py`、`retrieval/index.py`、`retrieval/context.py`、`retrieval/ranking.py`及配置项。程序关联若已满足相应行为，应复用而非重写。

索引版本递增，绑定原始知识、关联策略、候选策略、编码器、重排模型及参数的校验信息。知识原文及编码协议未变的向量，可以在来源ID和签名校验一致后复用；旧上下文缓存不得冒充新策略结果。原冻结目录与100题请求均保留。

## 7. 验证与验收

### 结构与筛选回归

- 1833条原始知识仍可完整定位，ID和原文零改写。
- 无关联知识仍可进入全局召回；错误的弱系统关联不阻断全局通道；多系统知识不因包含额外系统失去候选资格。
- Schema及训练案例的系统筛选行为不被放宽。
- 合并候选不会在精排前意外丢失全局候选，最终提示词的原文与日志一致。
- 地标坐标38条、医院定义10条、海事资料48条都具备全局检索资格。此项是资格检查，不等于实际召回率达标。

### 业务覆盖与噪声评价

| 指标 | 统计方式 |
| --- | --- |
| 必要知识候选召回 | 问题级金标在全局/合并候选池的Recall@50/@80，按通道和丢失阶段报告 |
| 最终knowledge覆盖 | 必要知识是否实际进入提示词，不能只统计knowledge字段非空 |
| 必要事实覆盖 | 跨knowledge、Schema、训练案例核对，区分441类“知识块未收录、案例已有公式”的情况 |
| 精确率与噪声 | 仅在有明确相关/不相关标注的范围计算；未标注不直接当负例，同时报告条数和token占比 |
| 表级关联 | 使用独立基准报告逐表precision/recall/F1及多关联/命中数，保留现有200%噪声约束及零命中单列规则 |
| 完整库表覆盖 | 对固定100题回归，完整业务库不低于99/100、完整表不低于95/100，并报告逐题变化 |
| 多库联查 | 同系统跨业务库和跨系统分别统计完整库、表、必要知识覆盖及最终SQL语义 |
| 性能 | 候选量、重排文档对数、耗时和token分布，与相同硬件、相同题目比较 |

已有8个知识缺口逐项追踪：441→1624、935→1581、1050→1590、2125→1689、2462→1706、2487→1709/1710、2908→1742。只在评价入口使用这些ID，不能在生产代码添加例外。它们是已发现问题清单，不是完整知识金标；最终必需性还要结合案例证据和原文冲突审查。

现有100题用于开发回归，不能因按这100题修复后分数提高就宣称独立泛化。新评估按同题/近似模板分组划分，验证答案不能进入案例池或训练增强；尚未核定的参考歧义单独报告。最终SQL语义评价应在知识召回效果确认后进行，并区分静态审查与数据库执行。

建议消融次序：旧版 → 仅增加全局通道 → 增加关联补充和名称候选 → 加相关性/冲突处理 → 加知识辅助补表。每一步同时观察覆盖、噪声和成本，不能只看最终单一得分。

## 8. 本次修复的边界

这套方案修复的是正确知识无法被检索、弱关联限制范围、以及提示词证据选择的问题。原始题面缺年份、参考SQL阈值写错、原知识残缺、新规则与旧答案冲突，需要独立的数据清理与口径裁定；扩大召回不能自动消除这些问题。
