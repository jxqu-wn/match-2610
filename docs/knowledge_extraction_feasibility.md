# knowledge.json 纯程序提取可行性分析

## 分析范围

当前 V5 的 `data/赛题8/knowledge.json`，共 247 条，ID 为 1554–1800。
源文件 SHA-256 为 `92f310bc19420e8b374936c1eac0b35b58489c2764a892976fdfae3268b276c9`。
逐条检查写法后，使用现有依赖和原始 Schema 在内存中验证格式、SQL 引用和字段定位。
没有调用模型，没有修改原始知识、关联算法或预处理数据，也没有生成运行产物。

约束：允许程序解析原文中已经给出的内容；不以人工或模型业务理解补全缺失字段、业务口径、
数据表归属、操作符、空间范围或关联关系。

## 可行性结论

- 全部原文无损保留、逐条记录处理状态：可以实现。
- 对有限、明确的写法进行结构化提取：可行，已有实测支持。
- 把所有自然语言含义无歧义地转换为可执行规则并定位到表：当前输入不足以保证。

“识别出某种写法”“提取出一个片段”“把整条知识完整结构化”“证明业务正确”是不同目标。
即使一个条目中的 SQL 已成功解析，条目前后的例外、限定、默认口径仍可能需要保留为原文。

## 当前可观察的写法

下表按表面标记统计；这些数量说明可检测的格式，不是完整语义提取成功率。

| 写法 | 条数 | 程序可直接提取的内容 | 边界 |
| --- | ---: | --- | --- |
| `SQL逻辑：…示例：SELECT…` / `SQL模式：…` | 18 | 定义段、逻辑/模式段、示例段、注意事项；示例 SQL 的表、列、别名、连接、过滤、聚合和排序等语法结构 | 15 条使用 SQL逻辑，3 条使用 SQL模式；后者包含英文伪代码，不能一律当作 SQL 执行 |
| 以 `表.字段 表示…` 开头 | 18 | 明确的表字段引用、解释原文、单位和明示的取值 | 缺少数据库名时须校验 Schema 唯一性，不能只凭字段名关联 |
| `名称的经纬度坐标为 (lat:…, lon:…)` | 38 | 地点名称、带轴标签的坐标、源位置；范围校验 | 范围合法不等于地理位置真实，也不证明坐标应归属某张表 |
| 带 `计算公式：` 标签 | 25 | 指标名称、公式原文、显式变量、单位、近似与本库限定等片段 | 中文变量、跨条目依赖和自然语言算式不一定是可解析 SQL |
| 含度分秒或度数记号的水域描述 | 46 | 显式坐标、方向、点标签、距离、半径、宽度、深度、约数及原文中的空间关系 | 实际边界未必完整，不能统一转成矩形、多边形或直线缓冲区 |

上述五类表面特征覆盖 145 条，其余 102 条包含代码/标签映射、条件定义、阈值、枚举、
同义词、时间规则、解释及它们的混合写法。145/247 也不是“可完全自动处理”的比例。

其他可复用的语法形态包括：

- `中文名称(CODE)`、`CODE=中文名称`：可抽取原文明示的代码—标签对应关系。
- `A包括B、C`：可保存枚举成员与原文关系，不能自动把它绑定到某个未明示字段。
- `定义：条件1 且/或 条件2`：对明确比较符和字段引用可建立表达式；没有明确字段的条件保留文本。
- `同义词：…`：可提取原文明示的别称，必须保留“仅当”等限制。
- `若…则…`、`通常…`、`本库…`、`近似…`：这些限定是信息的一部分，不得在提取公式后丢弃。

括号不一定代表同义词，也可能是单位、代码、条件、坐标或例子，不能按一种规则统一解释。

## 实测验证

### SQL 示例

知识 1554–1571 共 18 条完整 `SELECT` 示例，使用当前已安装的 SQL 解析依赖离线解析。
18 条均解析成功，物理表引用均能解析到当前 Schema，没有未解析的物理表名。
这证明当前示例的语法与表引用可机械提取，没有证明字段、计算口径、执行结果或自然语言解释正确。

例如 1555 的完整示例可以直接提取出 `ecommerce.orders`，无需从 `order_id`
反推 order_item、payment 等额外关联。别名、子查询和同名列应在 SQL 作用域内解析。

### 字段说明

知识 1604–1621 的 18 个 `表.字段` 引用，均在当前 72 张表/索引中唯一定位。
例如 `stocks.total_shares` 可以定位到 `MYSQL:finance_tax.stocks.total_shares`。
这是通过原文明确的表名与字段名联合查找得到的，不是根据“股本”的业务含义推断表名。

### 命名坐标

知识 1665–1702 的 38 组命名坐标均能提取为纬度、经度两个数值，并通过
纬度 [-90,90]、经度 [-180,180] 的范围检查。地点名称和原始精度应同时保留。
原文未给出坐标参考系统时，不额外认定其参考系统。

## 建议的程序处理方式

1. **原文与来源始终保留。** 每条知识保存原始文本、ID、源文件校验值。规范化文本用于解析时，
   保留规范化位置与原文位置的映射。
2. **组合解析器处理一条知识。** 同一条可以同时含定义、公式、SQL、单位、例外和注意事项；
   不强行把整条只分配给一种类型。规则描述语法，不按知识 ID 写业务分支。
3. **结构化结果只引用原文证据。** SQL 使用 AST 和作用域解析；明确表字段引用与 Schema 唯一性校验；
   代码、单位、坐标和枚举仅提取原文明示内容。不以字段同名或中文业务词推断表归属。
4. **完整记录未解析片段。** 每个结构化对象记录原文片段与位置；剩余片段单独保留，
   使用已解析、部分解析、未知、歧义、冲突或引用缺失等状态说明边界。
5. **知识与表的关联保持独立。** 能抽取坐标或业务定义，不意味着能给它指定 table。
   只有显式引用可确认为原文提及关系，其他知识独立保留供检索。

保留残余原文能保证信息不被丢弃，但不能据此声称残余内容已经被结构化理解。

## 验收应分别衡量

- **记录完整性**：247 条全部可追溯，原文不变，没有因不匹配而丢弃。
- **片段覆盖**：记录已识别与未识别的原文范围；每个非空白字符均有去向。覆盖数字只表示处理范围。
- **确定引用的正确性**：确认的表字段引用唯一可解析，每条边都有原文证据；歧义不强行通过。
- **结构性测试**：验证 SQL 别名/子查询、单位、比较符、嵌套括号、条件与例外、多坐标角色、缺失引用等。
- **语义边界**：统计部分解析、歧义和冲突，不能把“匹配一个正则”算成整条知识已完整提取。

建议先实现已实测可解析的 SQL 示例、明确表字段说明和命名坐标三类，
再逐步扩展公式、映射和条件解析；所有阶段都保留完整原文和未解析状态。
