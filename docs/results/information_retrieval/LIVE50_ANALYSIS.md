# 50题问题定位与改进优先级

日期2026-10-11。本次仅分析已冻结的50题输出与代码，不新增API调用，不把验证参考内容写入召回资料或提示词。

补充审计见[LIVE50_RETRIEVAL_ANALYSIS.md](LIVE50_RETRIEVAL_ANALYSIS.md)：6112的film_category原始排名7，进入初步候选集后被第一案例补表逻辑移除。因此“未召回”在原文指最终上下文缺表，不代表所有缺表均由检索排名不足造成。

## 关键结论

数据库系统分类50题均正确；50题没有token预算裁剪。19题未通过计划级语义审核，其中3题上下文缺必要表，16题参考所需表已提供。扩大token预算不能直接解决这16题的判断或口径问题。

目前的主要缺陷是：具体可检索缺口被当作最终失败提前终止，以及输出协议没有充分表达统计需求，结构校验只能证明字段/来源存在，不能证明需求覆盖。

## 1. 补检索控制存在明确缺陷

Planner.run只在status=need_more_evidence时继续。一旦status是insufficient_evidence，就直接结束，即使gaps中已经有missing_attribute、具体search_query且还有一次补充预算。

- 3602第一次判断直接返回insufficient_evidence，明确需要series_post。
- 303、6112首次选择了未提供的表，被结构检查正确拒绝；修复输出变为insufficient_evidence并附具体检索请求，程序随即结束。
- 三题expansion_rounds均为0。

本地关键词检索实际返回：303的dict_industry排第1；3602的series_post排第1；6112的film_category与category在各自请求中排第1。证明资料存在而且请求可用，但不证明补检索后模型必然正确。

优先修复：依据具体、合法、可执行的gap及剩余预算决定是否补检索，不只依赖一个status字符串。未知值域和意图歧义仍不能无限检索；结构修复仍不得扩大证据。对已存在catalog但未提供的表应先视为检索缺口，不能直接接受其为最终选表，也不能单纯逼模型删除它。

## 2. required_columns和assumptions没有形成覆盖约束

445已经提供corporate_income_tax_returns，但模型没有选它，只在假设里说需要用其中的revenue。程序不知道这是计算资产周转率必需的输入，因此接受ready_with_assumptions。

3509已经提供teams.games，但required_columns遗漏参考公式分母；2823提供完整AIS schema，却遗漏支持按船取最新记录的mmsi和timestamp。字段存在检查不能发现这些遗漏。

建议在同一次判断中输出结构化requirements与字段绑定，分别表示输出、条件、分组、聚合、排序、时间和业务范围。计算指标应列出分子、分母及引用字段。程序检查每个已声明必要引用是否落在selected_tables/required_columns中；业务需求的完整性仍由模型判断，程序不能凭字段同名推断需求。

不能通过把所有字段都塞入required_columns来解决，那会掩盖计划不明确的问题。

## 3. 缺少显式统计口径

4118需要先找评论最多的商家，再获取其类别；模型把它改为按类别汇总评论。1848的参考按匹配行计数，模型额外按课程名去重。341把字典精确名称扩大为包含外商投资/外资的模糊匹配。4079增加了参考没有的会议/期刊过滤，还没有选择对应字段。

建议结构化表达count_unit、group_by、distinct、filter.operator、filter.value、排序对象以及“先聚合/筛选谁，再输出谁”的阶段。对每个新增条件记录来源：问题、知识、训练案例或假设。未被明确要求、又会改变结果的条件不能仅因常识合理就加入。

相似案例可以提供连接和字段证据，不应覆盖当前问题的分组实体、时间、去重或统计单位。

## 4. 相似表缺少业务差异和选择约束

1632同时提供2024和2025课程表，题面未指定年份，模型默认选2025，参考为2024。应该显式报告业务范围歧义，而非默默选最新库。

5603同时提供Goalies和GoaliesSC，模型因为SHO是整数、主键更简单选择GoaliesSC。类型便利不能证明统计范围等价。当前两个表的描述都泛称赛季统计，未充分解释差异。应补充来源支持的统计范围/粒度/年度属性，无法确认时保留未决，不用推断描述编造业务定义。

445的两个资产字段已经描述为不同口径（财务摘要vs全年季度平均）；模型仍混用，说明描述存在还不够，需要将时间与统计口径纳入选择依据。

## 5. 关联关系缺少基数和结果保留语义

5694追加Coaches，coachID不是该表单列唯一键，可能复制Master行；4191追加Business连接，而源business_id可空，可能过滤原结果。外键证据不能证明额外连接对统计无影响。

应在关系中保留连接类型、关联字段是否唯一、可空性和计数粒度。仅判断存在记录时考虑半连接/EXISTS；若确实JOIN，应明确重复控制和保留无匹配记录的行为。不能把默认DISTINCT当通用修复。

## 6. 一部分不一致来自题面与参考的冲突

4149参考有Phoenix条件，与题面不符；3032题面说姓张，参考却用%张%；1632没有年份却固定2024；4288题面最多评论而参考用Uber级别。这些已经标记reference_anomaly。3509的比例分母也需要明确，题面不足以唯一指定参考的games分母。

需要分别报告“与参考一致”和“是否合理回答题面”。不能把为了逼近参考而加入隐藏城市、年份或公式写进生成提示词，更不能把本次验证正确SQL补进训练检索索引。

## 评估边界

82%是表集合匹配，62%是当前协议下的保守计划级人工审核，并非SQL执行等价率。现有协议不完整表达全部过滤、聚合、排序或连接类型；通过的31题只能说明信息覆盖与显式口径未发现冲突，不能证明完整SQL一定正确。

长期语义评估应基于更完整的结构化计划，或生成SQL后做结果级验证；人工审核保留无法确认类别。不能把unknown算通过，也不能把参考疑点排除后只报更高分。

## 建议实施顺序

1. 修复具体缺口没有触发补检索的控制流程，加入本地机制测试，不修改验证题的答案或检索材料。
2. 在同一次模型判断中增加requirements→字段/公式绑定和结构化统计口径；对引用了未选择表的计划拒绝ready。
3. 对关联基数、空值及相似业务库/表增加可追踪的检查和范围说明。
4. 将这50题保留为诊断回归，另取未用于调试的样本作为下一轮泛化评估，继续隔离训练案例与验证答案。
