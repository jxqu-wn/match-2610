# 680 题外部评分后的跨系统流程诊断

当前代码支持单系统跨业务库 SQL，也支持通过 `db1/query1`、`db2/query2` 和 `result` 生成跨系统查询。但本次运行没有可靠地识别跨系统需求，也没有在接受答案前检查需求完整性或实际执行结果。

本次仅核对现有输入、生成记录、代码和用户提供的外部汇总；没有调用 API、修改生成结果或调整预处理规则。原提交 SHA256：`dc613ba14f85952b20f6dc3e38b56406aae774cadf1d204e99cfc3aa261b1c5c`。

## 可直接核实的现象

按题目内容核对 ID 440–552 的 113 道船舶跨源题，其数量与外部 federation 分项一致。没有外部逐题类型标签，因此这里属于本地按题意识别的题组。

| 环节 | 统计 |
|---|---:|
| 初始路由 MYSQL | 41 |
| 初始路由 POSTGRESQL | 65 |
| 初始路由 MYSQL + POSTGRESQL | 7 |
| 初始提示词同时包含两系统 Schema | 7 |
| 最终仍是单系统查询 | 84（MYSQL 28、POSTGRESQL 56） |
| 最终为两步查询 | 23 |
| 最终为三步查询 | 6 |

路由预测直接限定首轮候选系统。仅召回单系统时，另一系统的必要表和字段不会进入首轮提示词；重排只会在这个受限候选集合内工作。训练与新问题的表达差异可能影响路由，但没有单独的路由归因实验，不能仅凭这些统计确定分类器为何误判。

部分答案缺少题目需求却直接通过静态校验，因而没有进入证据扩展重试。例如：

- 440 题要求船长姓名和最大航速，最终仅查询 PostgreSQL，返回 `mmsi` 与 `MAX(sog)`；生成记录承认没有船长姓名字段并以 MMSI 代替。
- 442 题要求最大荷载量和公司名称，最终将 `draught`（吃水）代替荷载量，将 `destination`（目的地）代替公司名称。这些字段存在，但业务含义不等价。
- 470 题要求指定经营类型公司所属船舶今天的平均航速，最终对 MySQL `vessel.max_speed` 求平均，未使用 AIS 当天航行记录。
- 520 题在 PostgreSQL 查询中使用未限定的 `name = '招商局'`；原始 AIS Schema 没有 `name` 列。当前校验仅检查可解析别名下的限定字段，漏检这种未限定字段。

这些是从答案与记录中直接观察到的缺陷，不依赖外部逐题得分。不能据此声称对应题目的外部失败原因已被执行日志证实。

## 当前校验的边界

`submission/validate.py` 检查键结构、合法系统、SQL 解析、只读、表引用、部分限定字段以及后续步骤是否出现 `result`。它没有：

1. 将题目需求与最终输出列、过滤、时间、统计对象逐项核对。
2. 阻止把明确缺失的字段或条件当作 assumptions 省略、替换。
3. 全面解析未限定字段、关联子查询和跨步骤输出类型。
4. 实际执行 SQL、替换 result、验证跨系统连接结果。

因此，先前的“680 条静态校验通过”仅说明通过了现有较弱的检查。它不代表需求完整、联邦执行成功或业务正确。原流程将这种校验成功作为生成结束条件，属于当前实现的验收缺口。

## 外部成绩能说明什么

外部报告 federation 仅 1/113、4.5/538.5 分。该分项损失 534 分，占总失分 1058.75 分的 50.44%，应优先修复。

实际生成的分步协议仅 29 份，不能将其当作 29 题正确。外部仅提供汇总，没有执行错误、每步中间结果或判题脚本，无法确认这些分步查询分别是否因空结果、SQL 错误、result 替换、日期基准或其他协议差异失败。尤其 6 份使用了三步协议，外部是否支持 `db3/query3` 尚不明确。

此前的 50 题实验衡量提示词库表覆盖率，没有执行 SQL；该抽样只有 2 道跨系统题。96% 的总体表覆盖率不能证明本次 113 道联邦题可以正确执行。

## 修复顺序

1. 将系统路由作为候选优先级，增加按需求检索另一系统的入口；先识别所需属性及其真实所属表，再确定单系统或跨系统计划。
2. 生成前明确输出、过滤、时间、聚合和跨系统连接键。船舶题可使用现有 Schema 与训练证据识别连接键，不能按本次题号或判题标签写生产白名单。
3. 对每项需求检查实际证据。缺失时扩大召回并重新规划，不将省略要求或语义不等价的字段替换视为完成。
4. 为现有 SQL 解析器补齐字段解析和跨步骤接口检查，包括中间结果列数、类型、result 消费方式及相邻同系统步骤的合并。
5. 使用独立验证集分别报告跨系统识别率、双侧表覆盖率、分步协议有效率与执行结果；有可用数据库时核对中间结果和最终执行，不以非空结果替代业务需求正确性。
