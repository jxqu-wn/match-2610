# table 与 knowledge 关联审计

## 范围与结论

本次审核 `data/catalog.py` 的预处理关联，以及 `retrieval/index.py` 中后续使用的两套关联。
用户要求预处理不得引入人工或大模型提供的额外业务理解，约束已写入项目根目录 `AGENTS.md`。
当前知识写法、纯程序提取的离线验证与边界见[提取可行性分析](knowledge_extraction_feasibility.md)。
本轮记录关联实现与实测问题，保留现有匹配算法供逐项审核，不把建议描述为已完成的修复。

当前实现没有提供关联准确率或完整率保证。它能保留部分原文，但预处理、索引文档和检索支持
使用不同规则，既会漏关联，也存在没有显式表引用证据的关联。

## 预处理中的实际原理

`link_knowledge()` 执行以下步骤：

1. 用 `(table.database, table.name)` 建索引，只收录 `database` 非空的表。
2. 每条知识只用一次正则 `search`，识别固定句式 `数据库X的表Y`。
3. 用提取出的数据库名和表名精确查索引，命中后把知识 ID 和完整原文加入该表的 `knowledge`。
4. 再按中文句式提取字段描述，将结果填入缺失的字段描述中；这一步不会增加 table 关联。

该过程不调用模型，也不理解知识业务含义。现有 `KnowledgeRef` 没有记录命中位置、引用种类、
歧义、拒绝原因等信息。它也没有验证“提到了某表”是否意味着整条知识都适用于该表。

### 可复现的边界问题

| 输入或条件 | 当前行为 |
| --- | --- |
| `使用 transportation.vehicle 的字段。` | 没有关联，因为不符合固定中文句式 |
| `数据库transportation的表vehicle和driver记录。` | 只关联 vehicle，遗漏 driver |
| `数据库missing的表unknown；数据库transportation的表vehicle。` | 首次匹配无法定位表，整条跳过，遗漏后续有效引用 |
| `数据库public的表vessel_ais_data。` | PostgreSQL 的 namespace 位于 `schema`，`database` 为空，未进入索引 |
| 数据库、表名大小写不同 | 当前匹配不做规范化，可能漏关联；正确规范化应服从数据源标识符规则 |
| 对同一目录重复调用函数 | knowledge ID 重复追加，未去重 |
| 同名库表出现在不同引擎 | 索引键未包含引擎，可能相互覆盖；当前数据没有用该情况证明安全 |

## 当前非 SQLite 输入的实测结果

直接从原始 Schema 和知识在内存中构建目录，并以空训练案例列表隔离知识关联逻辑。
测试不调用外部服务，也没有在 V5 中生成预处理文件或索引。

- 表/索引：72 个。
- 知识：247 条。
- 知识文件 SHA-256：`92f310bc19420e8b374936c1eac0b35b58489c2764a892976fdfae3268b276c9`。

| 关联位置 | 有关联的知识条数 | knowledge–table 边数 |
| --- | ---: | ---: |
| 预处理 `table.knowledge` | 0 | 0 |
| 索引文档 `table_ids` | 93 | 173 |
| 检索使用的 `explicit_knowledge_links` | 46 | 56 |

剩余知识均不符合预处理固定中文句式，因此 72 个 table 的 `knowledge` 都为空。
后续 `build_documents()` 对未关联知识，按知识中包含下划线的标识符与字段名交集补关联。
`literal_references()` 又用完整库表名、数据库作用域中的表名、唯一的表字段引用建立另一套关系，
在 `search_tables()` 的知识支持路径中使用；普通知识检索仍可使用文档中的宽松关系。

两套后续关系在 67 条知识上给出不同表集合。文档关系中有 121 条边没有得到
`literal_references()` 的显式引用规则支持，另有 4 条显式引用边未进入文档表集合。
152 条知识在这些路径中均无关联。这些是规则覆盖与分歧统计，不是业务关联准确率、召回率或错误数量。

### 实际例子

知识 1555 的 SQL 明确引用 `ecommerce.orders`，解释客单价的计算。
索引文档却通过同名 `order_id` 等字段，将其关联到 orders、order_item、payment 三张表。
后两条关系缺少原文中的显式表引用证据，当前程序没有证明它们适用。

知识 1761 解释行政区划代码，并提及 `area_id`；宽松规则把它关联到 8 张有该字段的表。
仅凭字段名称相同，无法确认这 8 个字段都具有知识中描述的编码规则。

## 质量和数量应如何验收

以下是后续修改的验收要求，当前实现尚未满足：

1. **关联有可复核证据。** 每条边保留知识原文、ID、命中片段及位置、表标识、解析规则。
   优先提取原文完整库表名和 SQL AST 中的真实表引用，正确处理引号、作用域、别名及引擎歧义。
   明确区分“原文提及”与“业务上适用”，不得将后者作为前者的自动推论。
2. **扫描全部显式引用。** 一条知识可关联多张表；未知引用不阻断后续引用；去重并保证重复执行稳定。
   表标识不存在或无法唯一解析时记录原因，不自行选择或补全。
3. **逐条交代知识去向。** 所有输入知识都进入审计清单，分别记录有证据关联、未匹配和有歧义等状态。
   没有表引用的通用知识独立保留，不强行分配给某张表；每张表允许零条知识。
4. **预处理与检索共享关联结果。** 下游不得再按字段同名悄悄新增已确认关联；相似度只能用于候选召回。
   展示每张表的关联数量及证据、无关联表、未匹配知识、歧义和失败原因。
5. **用结构性测试约束解析。** 覆盖多表、多次提及、未知表后继续扫描、跨引擎同名、引号与边界、
   SQL 注释/字符串、无关同名字段、重复 ID 和重复调用等情况。测试预期来自可控输入中的明确引用，
   不依赖新增的业务解释。

可以验证“每条已确认边都有来源”和“已定义语法范围内的显式引用被完整处理”。
没有独立的真实关联标准时，无法仅凭关联数量或这些测试宣称业务准确率、召回率达到 100%。
