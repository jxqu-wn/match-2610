# 裁剪、协议检查与遗漏优化

2026-10-11。总预算由12000提高至24000，输出仍预留3000；使用同一20题真实重测，旧版产物保留在live20，新版在live20_v2。没有增加验证题数量，没有将验证SQL答案发送给模型。

## 改动

1. 有embedding模型时，使用本地Qwen tokenizer计数×1.2＋256；关键词模式回退到字节估算。此为经验估算，不是DeepSeek精确tokenizer。首轮另预留4000供结构修复，避免追加输出和错误说明后挤掉证据。
2. 修复轮冻结schema、知识、案例和关系来源范围。超预算直接error，绝不删除原有schema来凑空间。有效字段/表/来源的检查仍保留。
3. requested_evidence接受非空字符串数组的等价转换，不补造缺失内容。模型已经列出假设但写ready时，规范化为更保守的ready_with_assumptions，避免无意义的模型修复调用。
4. 在表配额内补齐首个相关训练案例提到的表，替换低优先级候选；不把案例当作正确性保证。模型提示要求逐项检查输出、分组、条件、统计和实体名称，区分公司/车型名称与编码。
5. 保存模型原始输出和修复错误，便于后续定位。与旧版不同，错误分析能够检查实际响应而不是仅看报错摘要。

## 两倍额度与实际成本

配置总额度为原来的两倍，24000。本次重测实际总消耗却是旧版的2.35倍，原因包括保留更多资料以及3次冗余修复；不能将额度倍数冒充消耗倍数。

题6、2983、3012的首次结果已经有明确假设，只是status仍写ready。3次修复消耗23297 token，没有解决必要的资料缺口。加入status规范化后，用已保存首轮响应做本地回放，20题均通过结构检查且仍全部匹配参考表集合。所有首轮判断的API实测总计103682 token，为旧版的1.92倍。

因此，在该20题上省去这3次修复有望将后续消耗控制在两倍以内；这是基于真实首轮调用的本地回放，不是又一次完整API重测，也不保证其他问题都低于两倍。没有为验证规范化再次调用API。详见normalization_replay.json。

583题，仅本地检索，无新增API调用：预算内表召回率由80.42%升至97.14%，完整召回率由66.72%升至94.34%。原始Recall@8保持91.48%；补齐训练案例关联表和减少裁剪解释了预算内召回变化。
